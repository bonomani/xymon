NAME

test.cfg - per-test settings and test groups

 

SYNOPSIS

$XYMONHOME/etc/test.cfg

 

DESCRIPTION

test.cfg holds settings that belong to one test (one status column), in one place instead of spread over environment variables in xymonserver.cfg(5), and declares test groups. The file is optional: without it, or for a test it does not mention, everything works from the environment as before.

 

FILE FORMAT

The file is a list of blocks. A block is a keyword and a name, then its contents between "{" and "}". Inside a block, each statement is a keyword followed by its arguments, ended by a newline or ";". Blocks nest. Whitespace is insignificant, "#" starts a comment, and a word containing blanks can be quoted with double quotes.



    TEST myapp {


            HANDLER ncv


            GRAPHS myapp, myapp_errors


            METRIC myapp {


                    NCV requests:GAUGE errors:DERIVE


            }


    }


    group web {


            member http


            member https


            member apache


    }

A syntax error is reported in the log of the program reading the file, with its line number, and the whole file is then ignored: every test falls back to the environment.

 

TEST BLOCKS

TEST name { ... } holds the settings for the test "name".

HANDLER handler
The RRD handler that stores this test's data (see xymond_rrd(8)), for example "ncv" or "devmon". This takes precedence over the TEST2RRD environment variable for this test.

GRAPHS graph[, graph ...]
The graphs shown on this test's status page, replacing the GRAPHS_<test> environment variable. Commas between the names are optional.

METRIC name { ... }
A metric the test produces. When a test has exactly one METRIC and no HANDLER, the metric binds the test to an RRD handler: "ncv" when the metric carries an NCV or SPLITNCV statement, otherwise the handler named like the metric. Such an implicit binding never replaces a TEST2RRD mapping the environment already has for the test - the environment's mapping is kept and a warning is logged; use HANDLER to override it.

Inside a METRIC block:

NCV name:type [name:type ...]
SPLITNCV name:type [name:type ...]
The name-colon-value datasets to store, replacing the NCV_<test> or SPLITNCV_<test> environment variable (see the NCV section of xymond_rrd(8)). The pairs may also be written as a block, one per statement: "NCV { requests:GAUGE; errors:DERIVE }". An NCV statement without any pair is ignored, with a warning.

COUNTLINES
Page this test's graphs by the number of lines in its status message, as the tests listed in the --multigraphs option of svcstatus.cgi(1) are (disk, inode and a few others by default).

TEST and METRIC blocks also accept SOURCE, CMD, INTERVAL, PORT, TRACKMAX, and storage statements (EXCLUDE, STOREPATTERN, and blocks naming a storage backend). This version reads but does not use them; the graph-side storage filters are set in graphs.cfg(5) instead.

 

TEST GROUPS

group name { member test ... } declares a group of tests shown together. A member statement may name one test or several. The group name must not be the name of a test: the group takes over that column on the overview pages and its svcstatus.cgi page, so the test itself can no longer be viewed.

A group is for display only. It has no status of its own, sends no alert and cannot be acknowledged: its members keep their own status, history, alerts and acknowledgements.

On the overview pages generated by xymongen(1), a host's members are replaced by one column named after the group. Its light shows the worst colour among the host's members, and links to the group page: svcstatus.cgi with SERVICE=<group> shows a band with each member's colour, followed by each member's status, and the page itself takes the worst colour. A host with none of a group's members shows no column for it.

When svcstatus.cgi runs with --access, a user allowed to view the group sees only the members they are allowed to view: the others are left out of the band, the sections and the page colour.

"rollup worst" may be written in a group; it is the only rollup, and the default.

 

WHEN CHANGES TAKE EFFECT

Each program reads the file once, when it first needs it. The CGIs and xymongen start for every request or run, so they see a change at once; xymond_rrd must be restarted to see it.
