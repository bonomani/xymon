NAME

protocols.cfg - Configuration of TCP network services

 

SYNOPSIS

$XYMONHOME/etc/protocols.cfg

 

DESCRIPTION

protocols.cfg contains definitions of how xymonnet(1) should test a TCP-based network service (i.e. all common network services except HTTP and DNS). For each service, a simple dialogue can be defined to check that the service is functioning normally, and optional flags determine if the service has e.g. a banner or requires SSL- or telnet-style handshaking to be tested.

 

FILE FORMAT

protocols.cfg is a text file. A simple service definition for the SMTP service would be this:

   [smtp]
      expect "220" until "220 "
      send "ehlo xymonnet\r\n"
      expect "250" until "250 "
      options banner

This defines a service called "smtp". The lines are performed in the order they are written, which is the order of the conversation: xymonnet waits for a greeting beginning with "220", sends EHLO, and checks that the answer begins with "250". Any data returned by the service (a so-called "banner") will be recorded and included in the status message.

The order matters, and it is the only thing here that does. A service whose server speaks first is written with expect first; one that says nothing until it is asked -- clamd and spamd, for instance -- is written with send first. Writing before the server has greeted is a protocol violation in SMTP, and Postfix 3.9 and later reject the session for it.

A definition may hold as many steps as the conversation needs. Only the classic shapes -- a lone send, a lone expect, or a send followed by an expect -- use the single-exchange probe they have always used.

For services that require ALPN protocol negotiation (such as IMAPS multiplexed by Nginx on the same port as HTTPS), you can define:

   [imaps443]
      options ssl,alpn=imap
      port 443

The full set of commands available for the protocols.cfg file are:

[NAME]
Define the name of the TCP service, which will also be the column-name in the resulting display on the test status. If multiple tests share a common definition (e.g. ssh, ssh1 and ssh2 are tested identically), you may list these in a single "[ssh|ssh1|ssh2]" definition, separating each service-name with a pipe-sign.

send STRING
expect STRING
Defines the strings to send to the service after a connection is established, and the response that is expected. Either of these may be omitted, in which case xymonnet(1) will simply not send any data, or match a response against anything.

An expect may say where the reply ENDS:

      expect "250" until "250 "

Without until one read is taken for the whole reply, which is wrong for every protocol that answers on several lines: SMTP and FTP continue with "250-" and finish with "250 ", NNTP ends a block with ".", IMAP ends with the command tag. Naming the terminator reads to the end of the reply however it is split across packets. A greeting that arrives in two packets would otherwise have its tail matched as the answer to the next command, and a healthy server would be reported down.

The send- and expect-strings use standard escaping for non-printable characters. "\r" represents a carriage-return (ASCII 13), "\n" represents a line-feed (ASCII 10), "\t" represents a TAB (ASCII 8). Binary data is input as "\xNN" with NN being the hexadecimal value of the byte.

start FEATURE
Switch on something the CLIENT does. The word after start names code in xymonnet rather than anything sent to the server, and is reserved: tls is the only feature, and naming another is refused when the file is read.

start tls upgrades the connection where the line sits -- after the server has agreed to it, never before:

   [smtptls]
      expect "220" until "220 "
      send "ehlo xymonnet\r\n"
      expect "250" until "250 "
      send "starttls\r\n"
      expect "220"
      start tls

Everything before the line is plaintext and everything after it is encrypted, on the same socket. This is what SMTP on 25, submission on 587 and IMAP on 143 do, and it is the only way any of them reaches a certificate: the ssl option means TLS from the first byte, which is a different port and a different service. The certificate is read from the upgraded session, so a service that begins in plaintext reaches the sslcert column with its expiry checked.

Two words, because the action is not protocol-specific. FTP spells the request "AUTH TLS", POP3 "STLS", SMTP and IMAP "STARTTLS" -- but what the client does is the same in each, and the asking is left to a send, which is the only line that knows the protocol.

The ssl option is spelled that way for historical reasons; what both it and start tls negotiate is TLS.

port NUMBER
Define the default TCP port-number for this service. If no portnumber is defined, xymonnet(1) will attempt to lookup the portnumber in the standard /etc/services file.

options option1[,option2][,option3]
Defines test options. The possible options are 
   banner - include received data in the status message
   ssl - service uses SSL so perform an SSL handshake
   telnet - service is telnet, so exchange telnet options
   alpn=protocol1,protocol2 - specify ALPN protocols to negotiate during SSL handshake
